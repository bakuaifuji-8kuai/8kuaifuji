# 开发规格书：招采执行 — 框架协议采购·目录内比价

> 文档版本：v1.0 · 2026-11-09
> 对应页面：CompetitiveBiddingPage.tsx（招采执行）→ SupplierQuotePage.tsx（报价管理）→ SupplierQuoteSimulator.tsx（供应商端模拟小程序）
> 数据落地：Bidding（工单主表）、CatalogCompareItem（明细表）、BiddingQuote（供应商报价单）、ProcurementOrder（采购订单）
> 唯一下游：只有目录内比价会生成采购订单，其余 8 种采购方式直接走"无订单直接验收"

---

## 一、业务场景与定位

### 1.1 是什么
招采执行是整个招采域的"实质性执行环节"——从"招采需求确认通过"之后、到"生成采购订单（或直接验收）"之前的采购实施过程。

**目录内比价**（`framework_catalog`）是 9 种采购方式中**唯一走线上报价模式**的方式，其余 8 种都是"线下录入 + 提交审批"。它的核心差异：

| 维度 | 目录内比价（framework_catalog） | 其余 8 种（线下录入） |
|------|-------------------------------|---------------------|
| 明细结构 | CatalogCompareItem[]（线上报价明细表） | OfflineDetailItem[]（线下录入表） |
| 状态流转 | 走完整业务状态机（draft→published→bidding→evaluated→completed） | 只走审批状态（draft→submitted→approved/rejected） |
| 供应商报价 | 供应商线上提交报价单（SupplierQuotePage） | 采购方自己在工单手填中标结果 |
| 金额校验 | 单品上限 + 整单上限双控 + 比价结果汇总校验 | 清单合计金额手填校验 |
| 下游 | 自动生成采购订单 → 仓库收货 → 验收 | 无订单，验收页从需求明细兜底 |

### 1.2 上游来源
- **招采需求确认管理**（ProcurementDemandConfirmPage）：需求立项审批通过后，状态变 `confirm_approved`，可作为招采执行的来源
- **招采计划**：计划已审批通过，关联计划编号
- **合同**：目录内比价的每条物资可以关联到框架合同内/外（`contractScope: 'in' | 'out'`）

### 1.3 下游去向
- **供应商报价管理**（SupplierQuotePage）：目录内比价工单发布后，供应商可在报价页提交报价
- **采购订单管理**（ContractPurchaseOrderPage）：工单完成后一键生成 CPO 订单
- **仓库入库**：凭采购订单收货入库
- **招采验收**（ProcurementInspectionPage）：入库完成后走验收

## 二、状态机（目录内比价专属）

### 2.1 完整状态流转

```
    新建工单 → 保存草稿
         │
         ▼
    ┌──────────┐
    │   draft  │ ←── 编辑中，可反复改
    └────┬─────┘
         │ 点"发布"（校验: items 非空）
         ▼
    ┌────────────┐
    │ published  │ ←── 已发布，可设置招标时间
    └────┬───────┘
         │ 点"开始采购"
         ▼
    ┌──────────┐
    │ bidding  │ ←── 招标中，供应商报价窗口期
    └────┬─────┘
         │ 点"评审"
         ▼
    ┌──────────┐
    │ evaluated │ ←── 已评审，可上传评定结果
    └────┬─────┘
         │ 点"完成"（校验: 至少有 1 个合格报价）
         ▼
    ┌──────────┐
    │ completed │ ←── 已完成，可生成采购订单
    └────┬─────┘
         │ 点"生成采购订单"
         ▼
    采购订单管理
```

### 2.2 状态机按钮门控表

| 操作按钮 | 显示条件 | 不显示条件 |
|---------|---------|-----------|
| **发布** | `procurementMethod === 'framework_catalog'` 且 `status === 'draft'` | 任何其他状态 |
| **开始采购** | `procurementMethod === 'framework_catalog'` 且 `status === 'published'` | 任何其他状态 |
| **评审** | `procurementMethod === 'framework_catalog'` 且 `status === 'bidding'` | 任何其他状态 |
| **完成** | `procurementMethod === 'framework_catalog'` 且 `status === 'evaluated'` | 任何其他状态 |
| **生成采购订单** | `procurementMethod === 'framework_catalog'` 且 `status === 'completed'` | 任何其他状态或其他采购方式 |
| **设置招标时间 / 修改招标时间** | 目录内比价 + 审批通过后 + 状态 ∈ { published, bidding } + 截止时间未过期 | 非目录内比价 / 草稿 / 已评审以后 / 已过截止 |
| **上传评定结果** | 目录内比价 + 状态 ∈ { evaluated, completed } | 非目录内比价 / 其他状态 |

### 2.3 评审完成自动逻辑
点击"完成"时系统自动执行：
1. 筛选 `quotes` 中 `isQualified === true` 的报价单
2. 取 `totalAmount`（含税总额）最低的一家作为中标
3. 将中标供应商信息写入工单 `winningSupplierId` / `winningSupplierName`
4. 工单状态改为 `completed`
5. 如果无合格报价，弹窗提示"没有符合条件的供应商报价"并阻止完成

## 三、数据模型

### 3.1 主表：Bidding（目录内比价场景）

```typescript
interface Bidding {
  id: string;                       // 主键，'BID' + 时间戳
  biddingNo: string;                // 工单编号，保存时自动生成 JJ+年月日+3位序号
  procurementMethod: 'framework_catalog'; // 固定值

  // ===== 项目基本信息 =====
  projectName: string;              // 项目名称（必填）
  tenderer?: string;                // 招标人
  implementationUnit?: string;      // 招采实施单位
  projectImplementationUnit?: string; // 项目实施单位
  procurementHandler?: string;      // 招采经办人

  // ===== 关联上游 =====
  demandId: string;                 // 关联采购需求 ID
  demandNo: string;                 // 关联采购需求编号

  // ===== 目录内比价明细（核心）=====
  items: CatalogCompareItem[];      // 目录内比价明细表（见 3.2）

  // ===== 供应商报价 =====
  inviteSupplierIds: string[];      // 受邀供应商 ID 列表
  quotes: BiddingQuote[];           // 线上报价单（开始采购时自动模拟生成）

  // ===== 金额汇总 =====
  totalPriceLimit?: number;         // 整单含税上限（页面手填，保存时与 items.singlePriceLimit 合计比对）
  frameworkCompareAmountExcludingTaxInput?: number; // 比价结果汇总：不含税总金额（手填，保存时比对 items.supplierAmountExTax 合计）

  // ===== 招标时间 =====
  startTime: string;                // 招标开始时间
  endTime: string;                  // 招标截止时间

  // ===== 评审结果 =====
  winningSupplierId: string;        // 中标供应商 ID（完成时自动取最低报价）
  winningSupplierName: string;      // 中标供应商名称
  contractAmount?: number;          // 中标/合同金额
  awardTime?: string;               // 中标时间

  // ===== 状态 =====
  approvalStatus: 'draft' | 'approved'; // 审批状态（目录内比价简化：发布即 approved）
  status: 'draft' | 'published' | 'bidding' | 'evaluated' | 'completed'; // 业务状态

  // ===== 附件 =====
  biddingAnnouncement: Attachment[];   // 竞价公告附件（页面头部上传区）
  biddingDocuments: Attachment[];      // 竞价文件附件（页面头部上传区）
  attachments: Attachment[];           // 评定结果附件（最多 3 个，已评审/已完成后可上传）

  // ===== 审计 =====
  creator: string;
  createTime: string;
}
```

### 3.2 明细表：CatalogCompareItem

这是目录内比价工单的核心明细结构。**每条明细代表一个物料/服务项**，从采购需求明细自动带入，然后采购人补充上限单价等信息。

```typescript
interface CatalogCompareItem {
  // ===== 基础标识（从需求明细自动带入，不可改）=====
  productCode: string;              // 物资编码
  productName: string;              // 物资名称
  unit: string;                     // 单位
  quantity: number;                 // 数量
  specification?: string;           // 规格

  // ===== 合同关联（从需求明细自动带入）=====
  contractScope?: 'in' | 'out';     // 合同清单内/外
  contractRatePerMonth?: number;    // 合同费率（元/月，合同内物资才有）

  // ===== 采购人手动补充（必填）=====
  unitPriceLimitIncludingTax: number;  // 含税上限单价（必填，>0）
  unitPriceLimitExcludingTax?: number;  // 不含税上限单价（可选，与含税二选一）
  taxRate?: number;                     // 税率

  // ===== 需求明细原始单价（只读展示）=====
  demandUnitPriceIncludingTax?: number;
  demandUnitPriceExcludingTax?: number;
  costAuditUnitPriceIncludingTax?: number;
  costAuditUnitPriceExcludingTax?: number;

  // ===== 单价说明（下拉，固定选项）=====
  priceDescription?: '固定单价' | '上限单价'; // 仅这两个选项（2026-11-09 改动）

  // ===== 比价结果（保存时自动计算，基于不含税单价）=====
  demandUnitPriceExcludingTax: number;  // 不含税单价列（UI 显示列，保存时参与计算 supplierAmountExTax）
  supplierAmountExTax: number;          // 供应商不含税金额 = demandUnitPriceExcludingTax × quantity（自动算）

  // ===== 已废弃字段（保留兼容历史数据，UI 已隐藏）=====
  supplierUnitPriceExTax?: number;    // @deprecated 已被 demandUnitPriceExcludingTax 替代
  biddingFile?: Attachment;           // @deprecated 竞价文件改为页面头部统一上传
  winningSupplierName?: string;       // @deprecated 中标信息在主工单层面
  contractNo?: string;                // @deprecated 关联合同编号（已删）
  singlePriceLimit?: number;          // @deprecated 等同 unitPriceLimitIncludingTax
}
```

**⚠️ 关键字段解释：**
- `unitPriceLimitIncludingTax`：上限单价，保存时校验 > 0。这是供应商报价的参考基线。
- `demandUnitPriceExcludingTax`：UI 上的"不含税单价"输入列。**保存时系统用它 × quantity 自动计算 `supplierAmountExTax`**。这是比价结果汇总校验的数据源。
- `supplierAmountExTax`：自动计算字段，保存前由系统回填。**不要让前端在表格里手填这个字段**。
- `priceDescription`：单价说明下拉，**只有 '固定单价' / '上限单价' 两个选项**。选择 '上限单价' 时，供应商端小程序会显示灰色小字 "↑ 预算上限 ¥XXX/份"。

### 3.3 报价单：BiddingQuote（供应商侧）

```typescript
interface BiddingQuote {
```

## 四、校验规则（保存 + 发布）

### 4.1 保存前校验（handleSave）

| # | 校验项 | 校验逻辑 | 错误提示 |
|---|--------|---------|---------|
| 1 | 项目名称 | `projectName` 或 `biddingName` 至少一个非空 | "请填写项目名称！" |
| 2 | 明细非空 | `items.length > 0` | "请先选择采购需求，需求中的物资将自动带入！" |
| 3 | 单品上限 | 每条 item 的 `singlePriceLimit` 或 `unitPriceLimitIncludingTax` > 0 | "物资「{名称}」必须设置单品上限单价！" |
| 4 | 整单上限 | `totalPriceLimit > 0` | "请输入整单含税上限总价！" |
| 5 | 比价结果不含税总金额手填 | `frameworkCompareAmountExcludingTaxInput > 0` | "请填写"比价结果汇总"不含税总金额！" |
| 6 | 比价结果与清单合计一致 | `frameworkCompareAmountExcludingTaxInput ≈ Σ items.supplierAmountExTax`（容差 0.01 元） | "比价结果不含税总金额与清单明细合计不一致！您填写：¥X 清单合计：¥Y" |

**⚠️ 重点理解 item 6 的数据路径：**

```
Σ items.supplierAmountExTax
    ↑
    │ 自动计算（保存前由 updateItem 函数回填）
    │ 公式：supplierAmountExTax = demandUnitPriceExcludingTax × quantity
    │         （不含税单价列 × 数量）
    │
    │ 2026-11-09 改动：之前是用已删除的 UI 列 supplierUnitPriceExTax 计算，
    │ 导致永远为 0。现在改用当前页面实际显示的 demandUnitPriceExcludingTax 列。
```

### 4.2 发布前校验（handlePublish）

| # | 校验项 | 校验逻辑 | 错误提示 |
|---|--------|---------|---------|
| 1 | 明细非空 | `items.length > 0` | "请先选择物资并设置单品上限后再发布！" |

发布动作很轻：直接把状态改为 `published` + 审批状态改为 `approved`。

### 4.3 开始采购（handleStartBidding）

| # | 动作 | 说明 |
|---|------|------|
| 1 | 状态改为 `bidding` | |
| 2 | 自动模拟 5 家供应商报价 | 每家以单品上限为基准，在 80%~115% 之间随机报价。任何一家超上限则 isQualified = false |

**⚠️ 当前实现是前端自动模拟**。真实后端方案：供应商在 SupplierQuotePage 提交报价 → 写入 Bidding.quotes。

### 4.4 评审完成（handleComplete）

| # | 校验项 | 校验逻辑 | 错误提示 |
|---|--------|---------|---------|
| 1 | 合格报价存在 | `quotes.filter(q => q.isQualified).length > 0` | "没有符合条件的供应商报价" |

评审完成后自动取含税总额最低的合格报价为中标方。

## 六、供应商侧：报价管理页（SupplierQuotePage）

### 6.1 功能定位
供应商登录后可以看到受邀的目录内比价工单，提交报价单。

### 6.2 核心流程
1. 供应商登录 → 看到受邀工单列表（来自 `Bidding.inviteSupplierIds`）
2. 进入工单详情 → 填写每条物资的报价单价
3. 提交报价单 → 写入 `Bidding.quotes[]` 一条新的 `BiddingQuote`

### 6.3 报价校验
- 每条物资报价单价不能超过 `CatalogCompareItem.unitPriceLimitIncludingTax`（单品上限）
- 报价总额不能超过 `Bidding.totalPriceLimit`（整单上限）
- 任一超限 → `isOverSingleLimit` 或 `isOverTotalLimit` = true → `isQualified` = false

## 七、供应商端：小程序模拟器（SupplierQuoteSimulator）

### 7.1 单价说明联动
当 `CatalogCompareItem.priceDescription === '上限单价'` 时，报价输入框下方显示灰色小字：
```
↑ 预算上限 ¥{unitPriceLimitIncludingTax}/{unit 或 "份"}，建议报价不得超过此价
```

数据源优先级：`unitPriceLimitIncludingTax` → `singlePriceLimit`（旧字段兜底）

### 7.2 上限判断（isOverLimit）
```typescript
function isOverLimit(item, row, priceDesc) {
  const limit = row.unitPriceLimitIncludingTax ?? row.singlePriceLimit;
  if (!limit) return false;
  // 目录内比价所有单价说明模式都要超限判断
  if (priceDesc === '固定单价' || priceDesc === '上限单价') return item.unitPrice > limit;
  return false;
}
```

### 7.3 选项变化（2026-11-09）
原来支持 `['固定单价', '上限单价', '费率结算', '按量结算', '按次计费']` 5 种。
现在 CompetitiveBiddingPage 只提供 **['固定单价', '上限单价']** 两个选项。
如果 Simulator 还保留旧选项，需要判断是不是有意扩展。

## 八、生成采购订单（handleGenerateOrder）

### 8.1 前置条件
| 条件 | 说明 |
|------|------|
| `status === 'completed'` | 只有已完成状态能生成 |
| `winningSupplierId` 存在 | 评审完成时自动写入 |
| 可以重复点击 | 每次新增一条订单（弹窗二次确认） |

### 8.2 生成逻辑
```
订单编号：CPO + genSerialNo（年月日+3位序号，系统自动生成）
订单明细：工单 items[] 映射
  ├ productCode    ← item.productCode
  ├ productName    ← item.productName / materialName / name
  ├ specification  ← item.specification / spec
  ├ unit           ← item.unit
  ├ quantity       ← item.quantity
  ├ unitPrice      ← item.unitPriceLimitIncludingTax（含税上限价作为订单单价）
  ├ amount         ← unitPrice × quantity
  └ taxRate        ← item.taxRate ?? 0.13

订单头：
  ├ supplierId / supplierName ← winningSupplierId / Name
  ├ sourceType: 'framework_bidding'
  ├ demandNo ← 工单 demandNo
  ├ status: 'pending'
  ├ deliveryDate ← 当天
  └ remark: "由框架协议采购 {biddingNo} 自动生成，共 N 项"
```

### 8.3 落地
- 写入 `ProcurementOrder` store（`addProcurementOrder`）
- 回写工单 `generatedOrderId`

## 九、常见易踩坑清单

| # | 坑 | 现象 | 根因 | 修复 |
|---|-----|------|------|------|
| 1 | tfoot colSpan 错位 | 合计行向右偏移或重叠 | 表头减了列但 tfoot colSpan 没同步 | 每次改表头必须同步改 tfoot 和空状态的 colSpan |

| 4 | 整单上限为 0 | 保存通过但后续校验失败 | 手填框没填或填了 0 | save 校验必填 + > 0 |
| 5 | 竞价文件列数据残留 | 历史工单 biddingFile 字段非空但 UI 不显示 | 2026-11-09 删了 UI 列 | 类型层字段保留不动，只删 UI 渲染层 |

| 7 | 生成订单后再点"完成" | 已完成的工单无法再点"完成" | 状态机单向流转 | 正常，不需要修复 |
